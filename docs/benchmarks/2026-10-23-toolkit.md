# Routing and real critical paths after toolkit adoption

These are measured GitHub Actions runs, collected on October 23, 2026. Raw
reports retain source run/attempt/head identities and job/step timestamps. They
contain no runner environment dumps. Runner-seconds sum executed job duration;
they are not billed minutes. All runs in the tables are successful attempt 1.

## Same-checkout README selection experiment

[Probe PR 18](https://github.com/gigaverse-app/ci-esta/pull/18) changed only a
README comment and was closed without merging. Both runs checked out merge
`0f979342720fad14c7e1c0ff3b7bd0dae163abd7`, joining head
`510775256ae3ecf943d994d1f21b0e6dc4ed5fab` to base
`78e5e2b078ce6d9b4df488a102c387f3548aa00a`. The second run added `test:full`.

| Run | Executed jobs | Runner-seconds | Creation to gate | Execution-only critical path |
| --- | ---: | ---: | ---: | ---: |
| [Selected](https://github.com/gigaverse-app/ci-esta/actions/runs/39862792267) | 3 | 49 | 45s | 30s |
| [Forced full](https://github.com/gigaverse-app/ci-esta/actions/runs/39863205566) | 5 | 105 | 88s | 53s |

That is **53.3% less runner work** and **48.9% lower observed gate elapsed** in
this one sequential pair. Quality, routing/gate regression tests, package build,
strict metadata checks and an installed-wheel smoke test remained required.
The selector and its conservative input declarations caused the lane savings;
these are not receipt-reuse or environment-cache savings.

The selected chain was `quality -> Validation gate`: 30s execution plus 15s
post-prerequisite/start delay. The full chain was `Evidence plan -> Python
compatibility -> Validation gate`: 53s execution plus 35s delay. Those delays
include scheduling/startup and do not establish a pure runner queue duration.

Raw reports: [selected](2026-10-23-toolkit/ci-esta-39862792267.json),
[full](2026-10-23-toolkit/ci-esta-39863205566.json).
The observer is outside the validation dependency graph; its separate runner
cost is excluded from this table, not claimed to disappear. This is one sample
with cache and scheduling noise, not a universal latency guarantee.

## Full adoption runs: where work actually blocks the gate

[Open the rendered Gantt and critical-path report](2026-10-23-critical-path.md)
for the pytest-selective run. The highlighted chain comes from workflow
dependencies; the table below it gives execution time, delay and slack.

| Project / run | Gate elapsed | Execution CPM | Runner-seconds | Observed dependency chain |
| --- | ---: | ---: | ---: | --- |
| [pytest-selective](https://github.com/gigaverse-app/pytest-selective/actions/runs/39862718435) | 498s | 397s | 902 | select-tests -> Windows/Python 3.11 -> gate |
| [Due](https://github.com/gigaverse-app/due/actions/runs/39862718626) | 541s | 522s | 1,006 | select-tests -> locked integration tests -> locked test gate -> gate |
| [pytest-obligation](https://github.com/gigaverse-app/pytest-obligation/actions/runs/39862718305) | 525s | 358s | 1,851 | select-tests -> demos -> gate |

These are full workflow-change runs, not matched speedup experiments. Due's
separate widget workflow and the PR-title checks are excluded from the main CI
totals. Its widget workflow has its own aggregate gate and report.

The analyzer reads each source workflow at its commit, expands the observed
matrix jobs, follows `needs`, and computes both the latest-finishing dependency
chain and execution-only CPM/slack. In this sample, improving obligation's
MongoDB job (312s execution slack) would save work but would not shorten its
execution critical path. The demos chain included 167s of scheduling/start
delay. Splitting more jobs can increase contention, so that is not automatically
the right remedy.

## Environment cache: restore proof, mixed timing benefit

Each pair below uses the same source head. The first run was a default-branch
push; the second was an explicit full manual run. Exact cache keys in the JSON
prove which environments were restored. Setup seconds cover the whole composite
step: Python/uv setup, download-cache restore, environment restore, locked sync,
and any in-step environment save. The later setup-uv post-step is excluded; do
not interpret this table as total cache lifecycle cost or workflow savings.

| Project / lane | First setup | Second setup | First / second environment state |
| --- | ---: | ---: | --- |
| Due lint | 6s | 4s | miss / hit |
| Due typecheck | 12s | 6s | miss / hit |
| Due locked integration | 6s | 9s | hit / hit |
| Obligation core Python 3.11 | 7s | 4s | miss / hit |
| Obligation MongoDB | 7s | 4s | miss / hit |
| Selective Linux Python 3.11 | 6s | 4s | miss / hit |
| Selective Windows Python 3.11 | 8s | 12s | miss / hit |
| Selective quality | 4s | 10s | miss / hit |
| CI-esta quality | 13s | 9s | hit / hit |

The sample does **not** establish a general cache speedup. Tiny installs can be
cheaper than cache restore; scheduling, runner image and network noise remain.
CI-esta's pair was already warm, so it is a restore control, not a cold/warm
experiment. Its first environment-cache push separately recorded misses with
5s and 7s setup in [run 39861001093](https://github.com/gigaverse-app/ci-esta/actions/runs/39861001093),
but a different lock identity prevents treating that as the matched cold half.
The useful guarantee is exact identity plus locked verification and recovery,
not that a cache hit makes every project faster.

To reproduce, read `/repos/OWNER/REPO/actions/runs/RUN_ID/jobs` through `gh api`.
For each job, subtract the `setup-cached-uv` step's start timestamp from its end
timestamp. In that job's log, retain `Cache restored from key: ci-esta-venv-...`
or `Cache not found for input keys: ci-esta-venv-...`. Do not confuse the separate
uv download cache with a complete-environment cache hit. Avoid publishing full
runner logs or environment dumps just to document these fields.
