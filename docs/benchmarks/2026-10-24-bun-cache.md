# Bun caching and reporting, 2026-10-24

Web's dependency installation is fast enough that a large cache archive does not
consistently pay for its transfer and extraction. Keep the small compiler and
Firebase CLI caches, use `setup-cached-bun` for measured frozen installation, and
set `cache-downloads: 'false'` for this consumer. Other consumers retain the
download-cache default and can run the same comparison before overriding it.

## Controlled dependency comparison

[Run 40134362184](https://github.com/gigaverse-app/gigaverse-web-app/actions/runs/40134362184),
head `d3a8efe2661ba19b6261f159e7cd14ca55a1b072`, uses Bun 1.4.2 on
`ubuntu-latest`. All four strategies check out the same source and run
`bun install --frozen-lockfile`. Attempt 1 uses isolated empty cache keys;
attempt 2 restores those keys on fresh runners. The no-archive strategy downloads
dependencies afresh on both attempts. The Bun executable itself remains cached
by `setup-bun` in all strategies.

| Strategy | Attempt 1 setup | Attempt 2 setup | Attempt 1 runner time | Attempt 2 runner time |
| --- | ---: | ---: | ---: | ---: |
| Previous download-cache setup | 36s | 22s | 53s | 39s |
| Shared measured download-cache setup | 32s | 25s | 47s | 41s |
| Installed `node_modules` cache | 34s | 19s | 51s | 34s |
| Shared setup without dependency archive | 29s | 18s | 51s | 36s |

Setup includes runtime setup, cache-key computation, restore, mandatory install,
save and setup post-actions. Shared setup also includes measurement publication.
Runner time includes checkout, SSH setup, consumer probes, footprint collection
and cleanup. GitHub timestamps have one-second resolution; a zero-second step
is below that resolution, not necessarily free. The installed-tree archive was
358,874,444 bytes; avoiding repeated manifest hashing during its post-action was
necessary for a fair comparison.

Each attempt executes four dependency jobs. Their summed runner time is 202s
and 150s, respectively; their first-start to last-completion windows are 53s and
41s. These are experiment costs across four competing strategies, not the cost
or saving of a production workflow. A fifth job independently checks the aged
Firebase cache and is excluded from those dependency totals.

The [retained timestamps and calculations](2026-10-24-bun-cache.json) also include
exploratory runs 40134037622 (attempts 1–3) and 40134139551 (attempts 1–2). Across
all seven no-archive samples, setup took 18–29s. Shared archive setup took 22–33s.
The exploratory installed-tree controls included unnecessary post-action hashing;
use the final pair above for that strategy. Each run's attempts keep its own
source head constant. Sources differ between experiments only in CI configuration.

These small samples do not establish a statistical speedup. They support a
consumer-specific choice: fresh Bun installation is competitive, avoids archive
save overhead and needs less cache state. Restoring an installed tree made the
locked install nearly free, but did not make total setup faster in the final pair.
Both TypeScript compilation and the full application validations remain mandatory.

After merging web PR 4267, reproduce with the manual `Bun cache benchmark`
workflow, then rerun the same run unchanged. Cache salts use the run ID, not the
attempt. The workflow verifies Biome and TypeScript executables after installation.
It is an installation benchmark, not an application validation substitute.

## A successful Firebase restore that still reinstalled

[Egress run 40133042550](https://github.com/gigaverse-app/gigaverse-web-app/actions/runs/40133042550),
attempt 1, head `5a8d2f2fb592cc24ee169e6e4a1b52f52b04ac42`, restored its
66,398,949-byte Firebase cache in 2s, then spent 78s preparing the CLI.
[Bun 1.4.2's launcher](https://github.com/oven-sh/bun/blob/bun-v1.4.2/src/runtime/cli/bunx_command.rs)
expires installed tools after 24 hours, including exact versions. Restoring an
immutable old archive therefore repeated installation on every run.

Web now probes the exact pinned executable with `--no-install --package`, checks
its reported version, then renews the two freshness timestamps used by the
unchanged harness command. Missing installations retain the normal install path.
This preserves the pinned tool rather than resolving its dependency tree again.

The Firebase job in the final benchmark restores that same old archive, explicitly
ages its package and executable timestamps by two days, runs the repair and then
executes the original `bunx firebase-tools@15.29.0 --version` command. Both attempts
pass, preparation takes 0–1s at API resolution, and neither the repair nor the
consumer command logs dependency resolution. This demonstrates the aged-cache
fix; it does not claim a full-workflow speedup from a cancelled validation run.

## Reporting and adoption evidence

Public action smoke 40133884022 verifies cold, exact-hit, fallback-hit and disabled
download-cache paths. Every path still executes frozen installation and publishes
source-bound measurements. Failed installation still fails the action.

Candidate observers 40133892036 and 40133384036 render real completed App Checks
40133042583 and Egress 40133042550. The
[App Checks sticky](https://github.com/gigaverse-app/gigaverse-web-app/pull/4267#issuecomment-6389687936)
shows runner labels/name/group, restore outcomes and timings. Non-Python reports
no longer ask for pytest instrumentation. Compiler/tool caches remain distinct
from validated Python environments and completion receipts.

This follows the existing Python seam: Backend uses `setup-cached-uv` with a full
environment cache, while AI's main test workflow sets `cache-environment: 'false'`.
Shared setup supplies correctness, defaults and measurement; the consumer chooses
the cache layer that pays for itself. No cache hit counts as passing tests, and
cache saved time remains unavailable without a comparable control.
